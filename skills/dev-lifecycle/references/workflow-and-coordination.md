# 工作流与 Agent 协作

在任务跨阶段、需要多个角色或多个 Agent 时使用。普通小改动可省略正式方案或复杂 DAG；项目业务 Bug 修复和需求开发默认先由独立 Codex 子 Worker 做需求分析，并通过 Harness 完成问题答复和需求确认。用户明确说不需要需求分析时才可跳过。

## 主流程与子 Agent 分工

- 主流程只负责派发角色匹配的子 Agent、维护授权/阶段门、跟踪 Run/Task/Dispatch 和交接；不亲自执行分析、排查、编码、测试、评审、生成页面或用户澄清。
- 子 Agent 承担各阶段实质工作。Harness 流程中，需求 Worker 通过 Orca `ask` 投递业务问题，Harness 展示问题并用 Orca `reply` 回传用户答复；coordinator 只传递状态和消息，不替用户或 Worker 作业务判断。
- 如执行者不可用，主流程只负责另派替代子 Agent；不得在主流程窗口接管工作。

## 阶段

```text
需求接收 → 需求澄清 → 方案规划（按需）→ 实现 → 评审/测试 → 验证
```

- **需求接收**：界定目标、涉及仓库/服务及授权动作。
- **需求澄清**：默认派发独立 Codex 子 Worker；Harness 流程用 Orca `worker-start --agent codex --model gpt-6-luna --effort <阶段选定强度>`，不继承可能选择 Sol/Astra 的默认配置，并核验 `launch.effective`。Worker 只整理业务目标、角色、业务流程、规则、用户可见行为、验收标准、已确认事实和待确认问题；不检查代码、数据库/Schema、接口、架构、配置或技术文档，不讨论技术可行性或实现方案，也不修改仓库文件。技术问题只注明“待技术分析”。用户明确指定其他 Agent/模型时遵从；Codex 不可用时说明并等待用户决定，不静默改派其他 Agent 或由 coordinator 接手。
- 明确答复直接记录并进入下一题，不复述已答内容再次确认；只有答案含糊或冲突时追问。确有帮助时可补充 1–3 个可选代码定位线索，允许回答“不知道，由模型自行查找”；只将用户提供的线索交给开发 Worker，不在需求阶段查代码，也不把未知线索作为阻断。
- **方案规划**：需求 Worker 收齐逐题答复并回传结论后，Harness 展示问题答复、结论和 HTML 评审页；用户明确点击“确认需求并继续”后，coordinator 才按原任务授权派发下一阶段。用户只要求需求分析时，确认后也不自行开始技术分析；端到端修复/开发授权则按范围继续。
- **实现及交付前检查**：默认 Grok `grok-4.7` 开发、Codex `gpt-6-luna` 独立验证，并按模型家族交叉使用；缺少合适的空闲终端时，coordinator 自动在当前 Run/worktree 启动并纳入 Dispatch，不要求用户提供终端。若模型启动失败或发生回退，通过 Harness ask 同步具体阻碍和选项。编码 Agent 开始改动前必须显式加载 `$ponytail full` 和 `$caveman`，包括简单任务及 Orca Worker；派发文本要明确要求加载，不能假设 Skill 会跨会话继承。Ponytail 约束最小完整改动和必要验证；Caveman 约束对话表达，写入代码、注释、文档和工单时遵守其持久内容例外。派发后核对 Agent 实际收到的指令和可观察执行信息，有证据才报告已加载。Agent 不支持 Skill 时，如实说明，并把适用规则写入任务指令。目标足够明确后开始，变更严格限制在请求范围内，并保留无关工作区改动。开发及返修 Worker 默认不执行行为测试、test-compile 或 Docker 验收，避免与独立 QA 重复；必须在实现 Task 内完成最后一次代码修改后的格式化（Java 仓库执行 `./format`）及协调者预先核验过的最小受影响模块离线增量 compile（固定 mvn-verified.sh，默认不带 -am）；派发时写入工具链绝对路径和可直接执行命令。格式化或编译失败就由该实现 Worker 在同一 Task 内修正并重跑，不能先报告开发完成、转入 QA 后再另开一个纯格式化/编译返工 Task。协调者从 transcript 核实格式化、编译结果和最终 diff 后，才将实现阶段标为完成并启动独立 QA。编译之后若又改动源码，必须重新格式化和编译。
- **GitLab MR 高风险返修**：独立评审须通读本轮完整远程 diff 和相关调用路径，把全部有证据的阻断/高风险发现一次性写入最终报告。协调者按发现 ID 合并成一个返修 Task；实现 Worker 一次处理整批并回报每项状态。整批未解决或用户未明确接受剩余风险前，不更新分支、不推送、不重新提交评审。之后只进行一次完整独立复审；新发现须先合并成一批，禁止逐条打回、逐条推送和反复创建小返修 Task。
- **评审/测试**：QA 先按最终 diff 把需求页业务用例映射到本轮修改的方法、分支、字段转换或数据填充，只测映射范围与直接回归；本地范围外编号回传 `not_applicable` 并写明 diff 依据，Harness 展示为“本轮不适用”，不计入失败；只依赖外部系统的编号仅放入不展示的 `excludedTestCaseIds`，不带说明或进入 QA 结果。所有需求编号须被本地结果或该 ID 列表归类，且至少一个范围内用例有真实通过证据。数据夹具必须符合字段语义：URL 使用带 scheme/host 的合法值，图片使用图片 DTO 或既有最小图片夹具；不能用普通字符串假扮图片或 URL。未修改上传/识别逻辑时，不跑上传或识别链路。外部 MQ、Dify、Redis、ES、HTTP 等按约定默认正常，完全排除于本阶段测试目标、用例结果和阻断说明；不连接、不索要返回值，也不报告为“未验证”。隔离本地代码所需的 stub/mock 仅是测试实现细节。涉及数据库读写仍按项目规则用 Docker MySQL 调真实 Service/Mapper 核对前后值。Maven、预算、夹具与复测要求按 [engineering-preflight.md](engineering-preflight.md)。
- **结果归属**：QA 证据只采用当前 Task/Dispatch 和最新实现轮次，忽略旧 Dispatch 迟到回传；实现更新后旧 QA 仅为历史。用户明确授权新一轮返修或重新验证时清除旧的有效跳过标记并更新阶段，历史跳过决定仍保留；同一实现轮次没有新授权不得自动恢复测试。
- **QA 决策与返修循环**：QA 每轮失败或缺少验收证据时，Harness 展示模型、状态、结论和失败证据，coordinator 暂停等待用户决定。用户选择返修后，把范围内问题交回原实现 Worker；修复后由独立验证 Worker 只复测受影响用例和直接回归路径。每次明确决定仅授权一轮返修和一次定向复测；再次失败须回 Harness 展示证据、已花时间及选项，收到新决定前停止派发，不能凭原始全流程授权无限循环。用户可以中断当前验证，或跳过剩余验证并指定下一阶段；Orca Task 和 Harness 均须记录“未验证”，不得报告通过。续办指令发送给当前 Run 的 coordinator；活动中的测试须先中断并确认停止，已结束的 QA 也可直接续办。
- **测试编译失败的 QA 归类**：若 Maven 停在 `testCompile`，必须记为目标测试未运行、相关验收未验证，不能只因生产代码 `compile` 成功就把 QA 标为通过或“已完成验收”。验证 Worker 应依据首个编译错误核对报错行、类型定义、包名、import 和模块依赖，区分缺少 import、测试夹具错误、生成源码缺失或真实依赖问题；将精确根因和最小修复建议送 Harness。只有用户已授权且测试改动属于该 QA Task 的允许范围时，才由验证 Worker 修复测试代码并按要求格式化、重跑聚焦测试；否则暂停等待 Harness 决定。未执行的目标用例数须明确报告为 0，不能把编译阻断包装成行为测试结果。
- **验证**：将重要验收条件对应到可观察的测试或运行证据，并指出未验证事项。开发和 QA 用 worker_done payload 的 dependencyNotes 回传本次直接依赖的未修改业务调用（caller/callee/purpose/verification/impact）；QA 更新实际覆盖，coordinator 回读 Harness 的“既有调用说明”，不得只留在终端。未测试的依赖也要说明，但不因此自动扩测或增加 Gate。

## Gate 与用户确认

### Harness 与 Orca 同步

- Harness coordinator 启动后先创建本工单对应的 Orca Run、“需求分析” Task，再派发独立 Worker；启动前不分析工单、不浏览 PingCode、不提业务问题。提示词必须保持角色一致，不能一边要求 coordinator 先分析，一边禁止 coordinator 分析。工单快照是 PingCode 数据来源，Worker 不应重复认证或查询。
- 在 Harness 展示问题前，确认状态接口有有效响应，并核对当前 Run、分析 Task、Dispatch 和 Worker 的归属。空响应、无效 JSON、404 或任一记录缺失都应作为同步/编排故障停止在确认门，不得当作“无待确认问题”或继续阶段。
- 问题、答复和结论按确切需求分析 Task/Dispatch 读取，不能混入同一 Run 的其他编排消息。只有 Orca `ask` 才是可同步的问题；普通聊天输出里的问句不能补作 `ask`，应报告阻碍并停止。

- 任何会改变业务行为、风险、验收口径或外部副作用的不确定项都须逐题取得用户答复。Harness 启动的流程必须展示需求结论并等待用户明确确认，不能因问题已答复、Worker 已完成或原任务已授权开发而自动越过该确认门。
- 需求 Worker 使用 `$grill-me` 完成业务分析和逐题澄清，默认提出 1–3 个必要的核心问题，一次一个并给推荐答案。通过 Harness 发起时，Worker 用 Orca 阻塞式 `ask` 将问题投递给 coordinator；Harness 展示问题，用户逐题答复后 Harness 用 `reply` 原样回传。资料已唯一确定或用户明确豁免澄清时可为零个问题。coordinator 不代问、不代答。
- 需求评审按“业务分析 → `$grill-me` 逐题澄清 → `$answer-me-with-html` 生成 HTML 流程图 → `worker_done` 回传 → Harness 展示 → 用户明确确认”执行。任务文本明确要求加载两个 Skill。HTML 展示业务流程、规则、验收、已答问题和未决项，不得将未确认内容标为已确认；使用捆绑脚本 `node <Skill目录>/scripts/am.mjs render`，不得手写 HTML/CSS。Harness 展示结论和页面，并提供“确认需求并继续”；未收到确认前不派发后续阶段。Harness 集成不可用时说明阻碍并停在确认门。
- 用户确认需求后，若原任务已授权端到端修复/开发，主流程按范围派发下一必要阶段，不重复索要开发授权；用户只要求分析、明确暂停或原始授权不涵盖后续工作时，确认后仍停在相应阶段门。需求确认不授权提交、部署等外部动作。
- 不要为了每个阶段都有文档而停下来。阶段结果只有在能帮助用户做重要决策时才单独汇报；否则可在授权范围内继续。
- 用户指定了流程、Agent 或窗口时应遵守；不得静默替换，也不能声称启动了实际并未启动的窗口。默认由独立 Codex 子 Worker 做需求分析；用户指定其他执行者时遵从该指令。
- 用户明确说旧功能、旧表或旧链路忽略、不再改动时，这是硬性范围边界：可以只读确认现行链路的切入点，但不得修改、迁移、补数据、兼容扩展或把新功能接入旧链路。
- 依赖或环境不可用属于环境阻碍，不等于实现缺陷。给出证据和安全的下一步。
- 用户在 Agent 执行期间提出状态、原因或操作问题时，视为临时追问；回答后必须恢复原 Run、Task、Dispatch 和等待/派发循环。只有用户明确暂停、取消、改换目标或关闭窗口时才停止，不得因追问自动结束编排或丢弃后续依赖。
- 用户表示当前正在自行测试，或要求“只处理我指出的问题”时，禁止自作主张启动/唤醒测试、编排、Grok、Codex 或其他 Agent，禁止主动运行额外测试、切换阶段或修改无关文件；只处理用户明确指定的最小修复，直到用户再次授权。
- 用户明确说无需复现或跳过 Bug 复现时，记录未复现及跳过原因，继续其已授权的分析/修复，不再以复现门禁阻塞；不得将推演描述成实际复现。
- 项目 `AGENTS.md`、项目测试文档或用户指令明确要求的验收必须直接执行，不增加二次确认门。会读写业务表时按项目规则在 Docker MySQL 调用真实 Java Service/Mapper 并核对前后值；只有规则未要求且涉及共享环境或外部系统的额外集成测试才先确认。目标库缺少表时，可按迁移结构建立专用测试库并保留供后续复用；测试结束不清理，只新增当前任务的唯一数据。
- 阶段交接采用事件驱动：Agent 用正确 Task/Dispatch 身份发送 `worker_done`，coordinator 核验身份、outcome、产物路径和 Worker 归属并 ack。需求分析 Worker 回传后必须等待 Harness 用户明确确认；其他阶段按原授权自动推进。问题答复、普通聊天输入或 `worker_done` 本身均不能替代需求确认。持续检查 mailbox，使用不超过 60 秒的 `check --wait` 有界等待；保留 Run、Task、gate 和 Worker 状态。需求 Worker 可用 `ask` 将业务问题送到 Harness，但 `ask` 不能代替阶段完成或用户确认。
- Harness 与 Orca 的状态修改必须形成可核对闭环：把用户的确认、阶段调整、停止/续办指令发送给当前 Run，等待持久回执并回读 Run/Task/Dispatch；只有核对成功后才更新页面。仅有前端本地状态或“发送成功”提示不代表 Orca 已接受。失败时展示同步错误并停在当前阶段，不得继续派发或把旧状态覆盖成新状态。
- **Harness 回传不得退化为普通聊天回复**：阶段结论、QA 阻断、用户决定及续办结果必须写入 Harness 当前工单/Run 的聊天或状态通道，并读取持久回执确认已展示；Orca 终端中的最终回复、`worker_done` 收件箱消息或本对话回复都不等于 Harness 已收到。没有可用 Harness 写入入口、Orca 回执失败或回读不到当前 Run/Task/Dispatch 时，明确报告同步阻断并停在当前阶段；不得把问题转给普通聊天让用户代为搬运，也不得宣称“已回 Harness”。
- **续办前核对活动终端绑定**：按当前 Run/Task/Dispatch 读取 Orca worker-show，核对 `worktreeId`、绝对路径、分支、终端句柄和终端状态。可见/保留的终端不一定是 Harness 可续办的活动 Agent；已完成 Dispatch 的终端不能仅凭仍显示在 UI 就认定活动绑定有效。若 Harness 报“找不到此 worktree 对应的活动 Orca Terminal”，保留原始错误并停止阶段推进；在 Harness 为同一个既有 worktree 重新绑定或启动新终端/Worker，再回读确认绑定。续接未提交改动时必须指定现有 worktree 的精确路径或 ID，禁止用“从 master 创建”替代续办。若当前 shell 没有 `ORCA_TERMINAL_HANDLE`，不得伪造 `--from` 或借用其他 pane 的句柄；改从真正绑定的 Orca terminal/Harness 入口发起，否则报告阻断。
- 用户明确要求终止慢测并继续时，将其当作控制指令而非测试结论：停止目标进程、将对应 Task 记录为失败/中断及“未验证”，确认 fence 后按指令进入下一阶段，不重复启动测试。Harness 的续办指令必须发送给当前 Run 的 coordinator，即使 QA Worker 已结束也能传递返修/跳过决定；活动测试要先通过中断操作停止并记录，再续办。只跳过复现的指令不等于跳过测试；用户明确跳过/终止验收时保留未验证标记，且不得声称验收通过。

## Agent 职责

- 独立 Codex 子 Worker 默认只负责业务需求分析；不承担该阶段的技术分析、方案规划、代码实现或测试，需求分析输出不得包含架构、数据库、接口、配置、代码、技术可行性或实施步骤。
- 技术点由 Codex 或 Grok 分析。需求 Worker 若发现需求依赖技术判断，只记录待分析事项，不尝试回答。
- 开发 Worker 默认使用 Grok `grok-4.7`；独立验证 Worker 使用 Codex `gpt-6-luna`。若 Codex 开发，则由 Grok 验证，保持两种模型交叉使用并核验实际模型/effort。没有同角色空闲终端时 coordinator 自动启动并纳入当前 Run，不要求用户提供终端；模型不可用或发生回退时通过 Harness ask 请求处理决定，不静默降级。验证 Worker 可补充测试代码，不改生产实现。
- 当独立性确实有帮助或用户提出要求时，使用不同会话/Agent；避免多人并行写同一工作区。
- 用户对 Agent 或工具的明确偏好优先于本文件默认选项。
- 项目内已打开且职责匹配、工作区正确、当前空闲的角色终端应按角色复用；Harness 需求 Worker 必须关联当前 Run 和 worktree，问题与结论通过 Harness 展示，不切换到绕过确认门的私聊。
- Agent 阶段完成后默认保留窗口和上下文，不主动关闭终端或销毁工作区；后续任务优先唤醒该窗口。仅在用户明确要求或确有资源释放需要时关闭，并记录关闭原因。
- 发送消息、发送中断、切换任务或执行命令前，必须核对终端所属 worktree、Agent 身份和任务归属；禁止影响其他任务的 worktree。目标不明确时只读检查并停止，不得试探性操作。
- 当前任务有既存 Orca Run 时，所有新 Agent、并行节点和交接都必须注册到同一个 Run，并保留 coordinator、mailbox、task、gate 和 worker 状态；不得创建脱离当前 Run 的孤立编排或重置已有编排。派发前先检查当前 Run 和 worker 归属。
- 用户报告已清理目标工单历史或已开启新 Agent 时，聊天中残留的 Run/Task/Dispatch ID 只能作为查询线索。重新查询 Orca 当前 Run、目标 Task 和 Dispatch 后，只有运行时仍能确认关联，才可称“仍绑定”；若目标记录已清理，不得依据旧聊天记录恢复或重派失败任务。

## 问题分流

- 需求歧义 → 回到需求澄清。
- 设计或依赖问题 → 重新评估方案。
- 代码缺陷 → 修复实现。
- 测试/运行问题 → 根据证据回到测试或实现。
- 服务、依赖、凭据或环境不可用 → 说明阻碍，必要时请求缺失输入。
- 安全或生产影响不明确 → 在执行风险动作前停止并征求方向。

没有新证据或新假设时，不重复相同的失败尝试。
