# 工程前置检查与验证

在新增数据字段、外部服务、文档生成、部署拓扑或生产类似行为时使用。

## 前置检查

从代码、脱敏样例、Schema 或用户提供的契约确认相关事实：

- 请求/响应结构、字段类型、空值和一对多关系；
- 展示/持久化值的来源及缺失时的处理；
- 下游服务的职责边界，以及业务逻辑应属于哪一层；
- 涉及媒体/存储时的访问路径、凭据边界和网络链路；
- 运行依赖、版本、字体/浏览器、模板加载和目标环境；
- 高资源操作的并发、超时、清理及错误处理；
- 哪些可观察证据能证明结果正确。

不能只根据字段名推断业务含义。只有缺失信息属于不可替代的业务契约时，才询问用户或报告阻碍；测试图片、加签/加解密样例等可替代输入优先复用仓库资源或自行生成，不要求用户提供整套 Nacos 配置。真实密钥、生产配置和生产数据不得复制进测试产物。

## 验证

- 修改前检查工作区和差异；保护无关变更。
- 将改动限定在用户要求的行为和直接调用链；测试仅覆盖本次改动及直接回归，不顺手修复或测试无关问题。评审发现的外围风险先单独报告，不能自动扩成新功能或架构改造；只有它会使本次验收失败或直接造成数据错误时才纳入本次修复。
- 对用户指定忽略的旧链路只做必要的只读辨识；不得修改其代码、表结构、数据或调用关系。新功能必须落在用户指定的现行链路中。
- 为变更行为补充或更新聚焦测试，覆盖相关空值和边界场景。
- 测试前简要告知针对性用例、数据和预期。仓库 `AGENTS.md`、项目测试文档或用户指令明确要求的验收直接执行，不再等待二次确认；仅对规则未要求、且会扩大到高成本、共享环境或外部系统的额外集成测试，先与用户确认范围和时机。结束后展示逐项结果、命令/环境、未执行项及阻断，不能只报告汇总数字。
- 需要连接本地不可达的真实 Elasticsearch、Redis、RocketMQ/MQ 等中间件的测试直接标记“未运行/跳过”；不查找公网地址、不连接外部实例、不反复重试。改动相关且使用 mock 的单元测试可按定向范围运行。
- Java/Maven 项目运行测试前，先读取项目实际测试配置，不要直接假设 shell 的 `mvn`、默认仓库和 JDK 与 IDEA 一致。用户当前 IDEA 配置基准为 Maven 3.8.6：`/xxx/path/to/apache-maven-xxx`，settings 为该目录下 `conf/settings.xml`，本地仓库为 `/xxx/path/to/maven-work`。每次仍须核验这些路径与 IDEA 当前设置一致且可用；若用户提供了更新配置，以更新值为准。优先检查 `.idea/workspace.xml` 中 `MavenGeneralSettings` 的 `customMavenHome`、`userSettingsFile`、`localRepository`；若文件缺失或值无法读取，以用户提供的 IDEA Maven 截图或路径说明作为本机开发配置依据。核实 Maven 安装路径和 `-version`、settings 文件、本地仓库及 JDK，并记录本次采用的版本与配置来源。仓库内有 `scripts/mvn-offline-verified.sh` 时，所有 Maven 编译和测试必须经该脚本执行；它从已核实的 settings 读取仓库路径并校验 JDK 11，不要自行补写 `~/.m2/repository` 或 `-Dmaven.repo.local`。脚本不存在时，使用已核实的 Maven 绝对路径和 `-s` settings；settings 已配置本地仓库时不要额外覆盖它。命令行必须使用核实后的 Maven 可执行文件和 settings；配置缺失、矛盾或脚本拒绝执行时先报告阻断，不得绕过门禁改用另一仓库。
- 这项核验是 Worker 构建/测试的开工硬门：协调者先核定并记录 `MAVEN_BIN`、Maven 版本、`JAVA_HOME`/Java 版本、settings、本地仓库、离线脚本是否存在，再把这些绝对路径和可直接执行的命令写进 Worker 任务。不得只要求 Worker“自行发现工具链”，也不得由 Worker 按 PATH、Maven 默认 settings 或 `~/.m2/repository` 选择替代配置。
- 开发 Worker 的完成门必须包含格式化与生产源码编译：派发实现 Task 前，协调者把已核验工具链和最小受影响模块离线编译命令写入任务；实现 Worker 在同一 Task 内，最后一次源码修改后先运行仓库规定的格式化（项目 Java 仓库为 `./format`），再运行该离线编译，并报告实际命令和完整结果。任一失败都在该实现 Task 内修复并重跑；不能把“开发完成”设在格式化/编译之前，也不能为补做这些开发完成条件而另开纯格式化/编译 Task。编译后再改代码时，重新执行格式化和编译。协调者核验 transcript 与最终 diff 后才派发 QA；QA 的 `testCompile`/测试结果仍由独立验证 Worker 验证，生产代码 `compile` 不能替代测试编译或行为验收。
- Worker 报告测试完成后，协调者必须从实际命令/transcript 核对 Maven 版本、Java 版本、`-s`/脚本参数及仓库是否与预检记录一致，并确认 Surefire 实际执行目标用例。任一项不匹配时，不接受该次结果作为验收证据；先纠正工具链，再只重跑受影响的定向命令。重复出现私有依赖缺失时，先在正确的本地仓库核对 POM/JAR，避免在错误仓库反复运行。
- 聚焦测试若失败于 `testCompile`，先读取首个完整编译错误，并在测试源码定位报错行；核对对应类型是否存在、实际 package、当前 import 和测试模块可见依赖。不能把“找不到符号”笼统归因为 Maven/环境问题，也不能只复跑命令。若类型存在于另一 package 且测试缺少 import，明确归因为测试源码编译错误并记录最小修复；缺依赖、生成类型缺失或生产编译错误则分别归因。测试类未成功编译时，Surefire 目标用例执行数为 0，所有依赖这些用例的验收条件均为“未验证/阻断”，不得报告测试通过。按 QA Task 授权修正后，触及 Java 要运行 `./format`，并重跑该聚焦类确认 Surefire 实际执行的用例及结果。
- Maven 报依赖缺失时，先比较实际 Maven 版本、settings、本地仓库路径和缓存来源，并在选定仓库中核对依赖声明及 POM/JAR 是否存在；错误仓库缺少缓存不代表开发仓库也缺依赖。不要在错误的默认仓库上反复重跑，也不要把 IDEA Application 能启动当作本次代码已编译或测试通过。用户明确要求补依赖时，按其授权在项目实际使用的仓库中补齐，并继续运行测试。
- 若 Maven 因环境问题确实无法执行，才用已有依赖 classpath 做定向替代验证：显式重新编译本次修改的源码到隔离输出目录，再运行相关测试；不可直接复用时间早于源码的 `target/classes` 或测试 class。替代验证只证明实际运行的用例，不能表述为 Maven 构建或完整测试通过。
- 先运行与改动对应的定向用例；仅当直接受影响的调用链无法由定向用例覆盖，或项目明确要求时，才扩大到最小受影响模块。无明确理由不运行无关模块或全量套件。运行格式化、定向测试和项目强制验收；如必要扩大后有失败，区分目标用例和其他既有失败，保留具体失败名称与错误。
- 涉及渲染/导出时，尽可能检查真实输出：内容、分页、字体、图片及上传/响应，不只看 HTML 或日志。
- 涉及服务集成时验证契约两端；若真实中间件在本地不可达，只做必要的静态检查或 mock 单测，并明确记录真实集成未运行及原因，不为此改连外部服务。
- 本地无法运行完整微服务链路时，分别验证本次涉及的服务边界与本服务逻辑；单测及仓库要求的模块验收通过后，把跨服务链路交给人工联测，并给出最短操作步骤。不得为本地联调新建一套模拟框架或为了测试而测试。
- Docker/MySQL 测试在运行前核对固定主键、测试数据清理和隔离库；测试数据应避免与残留行冲突。出现主键冲突先区分产品缺陷、夹具冲突和环境残留，修复确定的测试根因后只重跑受影响用例一次；没有新证据时不得重复相同命令或扩跑整套测试。
- 对测试命令设置合理超时并观察实际进度。测试明显超出聚焦验收成本、长时间无进度或疑似死循环时及时停止，记录命令、已观察结果和未验证范围；若用户要求继续流程，按控制指令将该测试标为“中断/未验证”并进入指定下一阶段，不把中断记为通过，也不再次启动同一测试。
- 准确记录命令和结果；区分通过、跳过以及环境阻断。

## Java 仓库习惯

遵守仓库当前的 `AGENTS.md` 和 `docs/agents/` 指引。该工作区使用 Maven，修改 Java 后按仓库要求执行格式化。若项目要求离线构建，默认保持离线；用户明确授权补依赖时，只按项目实际 settings 和本地仓库拉取缺失依赖，随后恢复离线构建和测试。私有依赖缺失时，报告具体解析错误，不得声称构建通过。
