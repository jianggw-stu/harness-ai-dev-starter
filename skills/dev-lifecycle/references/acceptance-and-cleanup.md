# 验收与清理

用户明确表示本轮测试/验收通过，或直接要求清理时使用。

## 先盘点并保留

清理前检查仓库状态并确认任务范围。必须保留：

- 源码、测试、用户已有修改和仓库/项目规范；
- 后续回归所需的稳定脱敏测试输入和图片夹具；
- 用户需要的最终交付物；
- 用户认可的存放位置中的持久结论和源码定位；
- 与当前任务无关或之前已存在的文件。

不要把原始 SQL、凭据、Token、密码、生产数据快照或即将过期的签名媒体 URL 留作长期测试数据；需要时应脱敏或替换。

## 可清理内容

仅清理已被结论/证据吸收且范围明确的临时资料，例如重复 handoff、中间分析/评审版本、临时访问检查、调试日志、重复截图和失败/中间渲染产物。不能因文件名含 `qa`、`playwright`、`review` 等词就删除源码或测试。

目录边界、文件归属或最终/临时属性不明确时，先保留并询问。重要二进制产物优先采用可恢复移动。禁止对仓库或工作区执行宽泛递归删除。

## 收尾

- 有长期记录价值时，汇总最终结果、稳定规则、源码位置、测试数据、验证命令/结果和已知限制。
- 产品业务知识与本流程 Skill 分开，按用户选择存入项目知识或私有业务资料。
- 用户或仓库没有要求时，不机械创建 `final.md` / `rules.md`。
- 清理不包含自动提交、推送或部署；这些动作必须由用户明确要求。

## 删除完整流程

用户要求删除某工单的流程、重新从头运行或清理该任务时，按目标归属完整盘点并清理：

- Orca 的 Run、Task、Dispatch、Worker、消息、确认门及目标专属运行记录，按 `$orca-history-cleanup` 执行。
- 目标专属 worktree、对应本地分支和远程分支。删除前核对分支名、worktree 归属、远端和关联 MR；不得删除共享分支或其他任务正在使用的分支。分别确认本地和远程删除结果。
- 对应的代码评审 Task/Dispatch、评审报告和可精确定位的评审评论/记录。
- 若已有 GitLab MR，使用平台支持的定向操作关闭该 MR，并删除可定向删除的评审内容；平台不支持物理删除的 MR/评论应保留并报告其状态，不得把“已关闭”描述为“已删除”。

完成后分别核对 Orca 记录、worktree、本地分支、远程分支和评审/MR 状态。任一资源因共享、归属不明或平台限制未能删除，都要列出具体资源和原因，不能笼统报告“流程已全部删除”。
