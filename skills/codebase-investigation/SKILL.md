# 代码库定位与测试拆分

适用于已有仓库中的 Bug 修复、功能改造和重构。跨模型、Agent 与语言使用；项目指令和用户要求优先。

## 定位代码

1. 先把用户确认的行为转成可检查的条件。做修改时先确认工作区已有改动，避免覆盖无关内容。
2. 用一轮批量搜索找功能入口、关键状态/字段、直接调用方及相关测试。优先用 `rg`；合并可独立的查询，避免一次只搜一个词、再逐个重复读取。
3. 沿真实调用链读取必要方法和局部代码段：入口、核心分支、异步消息/事件消费者、结果处理或持久化点，以及对应测试。大型文件只读相关符号附近；仅在当前证据指出新边界时扩展范围。
4. 记录已验证事实、根因假设和未知项。足以解释触发条件、影响到的直接调用方、外部副作用及验收场景后，停止探索并开始实现；不要为了穷尽仓库而继续搜索。
5. 简单任务定位超过约 5 分钟仍未收敛，或搜索范围连续扩大时，先向协调者汇报已查路径、证据、假设和具体缺口，再按缺口决定是否扩查。复杂任务应在派工时设定相称的定位预算；不要把此时间提示当作跳过必要分析的理由。

不重复没有新假设支撑的全仓搜索，不反复读取同一大文件，不用改动行数替代根因证据。新增搜索应能回答一个明确的未知问题。

## 并行编写单元测试

先确认验收行为和最小调用链，再判断单测是否适合并行：

- 中大型改动中，若测试场景已明确、测试文件可与生产代码分开负责，可派独立测试 Worker。开发 Worker 只改生产代码，测试 Worker 只改指定测试文件；双方共享同一行为契约和目标接口。测试需要依赖新接口时，开发 Worker 先给出接口约定。
- 小型局部修复或测试强依赖实现细节时，由开发 Worker 编写测试；也可让测试 Worker 只整理用例，不另派写入者。
- 同一工作区写入必须按文件明确所有权；不能让两个 Worker 同时编辑同一文件。无法隔离文件时，使用独立 worktree 或串行执行。
- 并行测试草稿合并后仍须针对最终代码运行；独立 QA 继续负责检查最终差异和验证证据。

不要为并行而拆任务。若测试准备和协调的成本可能高于节省的开发时间，就由同一个 Worker 完成。
